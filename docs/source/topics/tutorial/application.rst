Application
===========

In this tutorial we will take a look at the event-sourced application in more detail.
By now you should have your domain model implemented as a set of event-sourced aggregates, but how do you use them and,
most importantly, how do aggregates interact with each other?

The tricky part is that you do not use aggregates directly. They are hidden behind another layer called ``Application``,
which we will discuss in this tutorial.

Every business domain has a set of scenarios that lead to a specific outcome - so-called use cases. Use cases are
triggered by an actor (a user or system) and this is the place where your aggregates start their lifecycle,
communicate with each other and change the state of the system by executing business logic and generating domain events.
The ``Application`` class is the place where you implement all use cases that exist in your domain.


.. code-block:: python

    from bestagon.core.event_processor import Application

    class BondsApplication(Application):
        pass


In addition to use cases, an ``Application`` fulfills several very important functions:

1. The application owns a domain model - each application is a place where a specific domain model lives and each
   aggregate belongs to exactly one application.
2. The application implements use cases where you create new aggregates and execute business logic using already
   existing aggregates.
3. It holds a reference to a repository which helps you to persist changes in the aggregates and retrieve already
   existing ones from the event store.
4. Last but not least, the application allows you to react to the events that have happened in any domain across
   your system.

You can think of an application as a microservice inside a microservice - it is a boundary with strict borders
where each application has its own domain model, knows nothing about other applications,
but can react to events generated by other domain models.



Application initialization
--------------------------

Let's start dissecting the ``Application`` class step by step. It is an abstract class that contains several abstract
methods that should be reimplemented after subclassing. We will return to them a bit later, but first, let's take a look
at application initialization.


.. code-block:: python

    from bestagon.core.event_processor import Application

    class BondsApplication(Application):

        def __init__(self, repository: EventSourcedRepository, checkpoint_store: CheckpointStore):
            super().__init__(repository=repository, checkpoint_store=checkpoint_store)


The application's ``__init__`` method takes two parameters as input:

- ``repository`` - an instance of the ``EventSourcedRepository`` class, which is responsible for the persistence and
  retrieval of aggregates.
- ``checkpoint_store`` - an instance of the ``CheckpointStore`` class, which is responsible for tracking which events
  have already been processed.


.. note::

    In most cases you do not need to reimplement ``__init__`` because applications are mostly stateless and you
    can directly proceed to the implementation of use cases.


Defining use cases
------------------

Let's take a look at how to implement use cases for a specific application.

Each use case is a method, named according to the name of the operation in your domain, for example ``issue_bond``,
``create_customer`` and so on. Besides ``self``, it must take one and only one parameter - an instance of the
``CommandMessage`` class that contains the necessary command in addition to the metadata.

The data from the command is used to create new aggregates or retrieve existing ones and execute the necessary business
logic on them. When writing your use case you usually implement it as a set of steps:

1. Validate the input to ensure that it contains the right data.
2. When creating a new aggregate, check for duplicates and return if the aggregate already exists.
3. Create a new aggregate OR retrieve the existing ones and execute business logic.
4. Save the changes to the repository.

.. note::

    It is highly advisable to stick to this rule of thumb when writing use cases - modify only one aggregate at a time.
    Your use cases, even if they involve multiple aggregates, should lead to changes in only one of them.


When saving an aggregate in the repository you provide it with the aggregate that has changed and the message
that was the reason why the changes happened (in most cases it will be the command message passed to the use case).
It is necessary to propagate the metadata from message to message.


.. code-block:: python

    class BondsApplication(Application):

        # The command handler name reflects your business domain and it receives a command message as input parameter
        async def issue_bond(self, command_message: CommandMessage) -> None:
            command: IssueBond = cast(IssueBond, command_message.command)

            # Here you can add validation logic for your command values
            # If the data inside the command is corrupted, then the use case should fail with an exception

            # Before creating a new aggregate we check for duplicates and return if this bond has already been issued
            aggregate_id = Bond.create_id(isin=command.isin)
            if await self.repository.contains(aggregate_id=aggregate_id):
                logger.info(f'Duplicate bond {command.isin}')
                return

            # Create a new aggregate and save it in the repository
            bond = Bond.issue(command)
            await self.repository.save(aggregate=bond, trigger_message=command_message)


.. note::

    Your use cases have to be implemented as async methods.


In addition to use cases, it is a good practice to add getters to your application to retrieve aggregates from the
repository. This will allow you to simplify your use cases and concentrate on your business logic.

.. code-block:: python

    class BondsApplication(Application):

        async def get_bond(self, isin: str) -> Bond:
            aggregate_id = Bond.create_id(isin=isin)
            bond = await self.repository.get_by_id(aggregate_id=aggregate_id)  # Raises AggregateNotFoundError if no such aggregate.
            return bond


Let's add a couple more use cases to the application - we need to be able to update the term to maturity of the bond
and set the bond as matured:

.. code-block:: python

    class BondsApplication(Application):

        async def set_matured(self, command_message: CommandMessage) -> None:
            command = cast(SetMatured, command_message.command)
            bond = await self.get_bond(isin=command.isin)
            if bond.ready_to_mature():
                bond.set_matured()
                await self.repository.save(aggregate=bond, trigger_message=command_message)

        async def update_term_to_maturity(self, command_message: CommandMessage) -> None:
            command = cast(UpdateTermToMaturity, command_message.command)

            # First get the bond from the repository
            bond = await self.get_bond(isin=command.isin)

            # Execute business logic in your aggregate
            bond.update_term_to_maturity()

            # Save changes in the repository
            await self.repository.save(aggregate=bond, trigger_message=command_message)


Reaction to events
------------------

Event-sourced systems are all about events - they are the source of truth from which the final state of the system can be
reconstructed and, at the same time, they are a driving force of the system - we can react to events and
execute use cases automatically as a reaction to specific events.

The application provides such a mechanism out of the box: each application contains a subscription to the event store,
and each time a new event appears it is propagated to the application, which provides an event handler that triggers a
use case.

To make it work you need to implement the ``get_event_routing`` abstract method. It takes no input parameters
and returns a dictionary where keys are types of events you want to react to and values are the corresponding event
handlers.

.. code-block:: python

    class BondsApplication(Application):

        def get_event_routing(self) -> dict:
            routing = {
                Bond.Issued: self._when_bond_issued,
                Bond.TermToMaturityChanged: self._when_term_to_maturity_changed,
            }
            return routing


Each event handler is an asynchronous method defined in the application which takes one and exactly one
parameter (besides ``self``) - an instance of the ``DomainMessage`` class. Inside each event handler you first construct
an instance of the ``CommandMessage`` class and then use it to trigger the specified use case.

.. note::

    It is a good practice to define event handlers as protected methods because they should not be a part of the
    application's public interface and are used only internally.


.. code-block:: python

    async def _when_bond_issued(self, domain_message: DomainMessage) -> None:
        domain_event = cast(Bond.Issued, domain_message.event)

        command = UpdateTermToMaturity(isin=domain_event.isin)
        command_metadata = CommandMetadata.from_domain_event_metadata(domain_message.metadata)
        command_message = CommandMessage(command=command, metadata=command_metadata)

        await self.update_term_to_maturity(command_message)

    async def _when_term_to_maturity_changed(self, domain_message: DomainMessage) -> None:
        domain_event = cast(Bond.TermToMaturityChanged, domain_message.event)

        command = SetMatured(isin=domain_event.isin)
        command_metadata = CommandMetadata.from_domain_event_metadata(domain_message.metadata)
        command_message = CommandMessage(command=command, metadata=command_metadata)

        await self.set_matured(command_message)


Application name
----------------

There is one more abstract method that is left uncovered - ``get_name``.
Similar to an aggregate, which should have a unique ID, your application should also have a unique identifier - its name.
It is used internally by the system and **should not be changed** after you define it, because the framework
uses it to create the name under which your checkpoints are stored, and changing the application name can lead to a
replay of all events from the beginning, which can corrupt your system.

.. code-block:: python

    class BondsApplication(Application):

        def get_name(self) -> str:
            return 'bonds_application'  # Unique across your system
