Event-Sourced System
=====================

Congratulations on making it this far! By now you should have an understanding of how to define your domain model
using a set of event-sourced aggregates, write use cases using applications and read models with projections, and now
it is time to tie everything together using the ``EventSourcedSystem`` class.

This component fulfills two very important functions:

- It orchestrates the communication between all other components, especially applications and projections.
- It serves as a boundary that separates your system from the outside world.

The second function deserves a better explanation. Imagine a medieval castle - in the center it has a great hall where
all the important decisions are made - this is your domain model. The castle is surrounded by a high wall and nothing
from the outside can't reach the great hall without passing the gate and guards. The ``EventSourcedSystem`` serves as
a high wall that protects your domain model from the exposure to the outside world, and this wall has a gate that allows
messages to pass in a form of commands and queries.

This gate is implemented as a couple of methods:

- ``execute_command`` - which takes a ``Command`` as an input and executes it using the registered command handler.
- ``execute_query`` - which takes a ``Query`` as an input, executes it using the registered query handler and returns the result.

Such a boundary is crucial for the whole system to work properly - you should never expose your domain model to the outside
world to protect your invariants.

Defining the system
-------------------

To create a system, use the ``EventSourcedSystem`` class:

.. code-block:: python

    from bestagon.core.system import EventSourcedSystem


    class BondsSystem(EventSourcedSystem):
        def __init__(event_store: EventStore, checkpoint_store: CheckpointStore, neo_driver: AsyncDriver):
            super().__init__(event_store=event_store, checkpoint_store=checkpoint_store)

            self.repository = EventSourcedRepository(event_store=event_store)
            self.bonds_application = BondsApplication(repository=self.repository, checkpoint_store=checkpoint_store)
            self.bonds_projection = BondsProjection(checkpoint_store=checkpoint_store, driver=neo_driver)

The system takes several parameters as input:

- event_store - an instance of the ``EventStore`` class to store events generated by your model.
- checkpoint_store - an instance of the ``CheckpointStore`` class to store information about the last processed event for applications and projections.
- Additional parameters, necessary for your system. In this case, it is an instance of AsyncDriver to access the Neo4j database.

Next, we create an instance of the ``EventSourcedRepository`` class. It will be used by applications to save and retrieve aggregates.
Unlike the traditional approach, where you create a separate repository for each aggregate, event-sourcing allows us to
greatly simplify this pattern and use a single repository for all aggregates.

After the repository, you define your applications. Here we have only one application - ``BondsApplication``,
which takes the repository and checkpoint store as parameters. Similarly, you add projections.
In our example, there is only one projection - ``BondsProjection``, which takes the checkpoint store and Neo4j driver as input parameters.


System initialization
---------------------

It is not enough to define your applications and projections inside the system.
To make it work, you need to initialize them and create subscriptions in the event store.
For that purpose, you need to reimplement the ``initialize`` method and add your applications and projections to the system.
To add applications, use the ``add_application`` method; to add projections, use the ``add_projection`` method.
Under the hood, the framework will make the necessary initializations and create subscriptions to the event store.

.. code-block:: python

    class BondsSystem(EventSourcedSystem):

        async def initialize(self) -> None:
            await super().initialize()
            await self.add_application(self.bonds_application)
            await self.add_projection(self.bonds_projection)


Routing commands and queries
----------------------------

The last thing to do is to register command and query handlers, so the system would know how exactly to execute commands and queries.
For that purpose, you use an instance of the ``Mapper`` class and use its ``register_command_handler`` and ``register_query_handler`` methods.
One place to do that is inside ``register_command_handlers`` and ``register_query_handlers`` of the ``EventSourcedSystem`` class:


.. code-block:: python

    class BondsSystem(EventSourcedSystem):

        # Registering commands and queries inside the system
        def register_command_handlers(self) -> None:
            command_handler_registry.register_command_handler(IssueBond, self.bonds_application.issue)
            command_handler_registry.register_command_handler(UpdateTermToMaturity, self.bonds_application.update_term_to_maturity)
            command_handler_registry.register_command_handler(SetMatured, self.bonds_application.set_matured)

        def register_query_handlers(self) -> None:
            query_handler_registry.register_query_handler(GetBondsQuery, self.bonds_projection.get_bonds)


After that, your system is ready to be used. In the next tutorial, you will learn how to serve your system across the network using FastAPI.
